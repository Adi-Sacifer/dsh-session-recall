# dsh-session-recall —— 让 AI 能翻自己别的对话

一个小巧、零依赖的工具，让 AI agent 在**任务被拆到两个对话里**的时候，能**主动去另一个框里翻**，
而且**不会把整份对话塞进上下文**。

```
scripts/sess.js    ~14 KB，纯 Node，不需要任何包
```

**[English README](README.md)**

---

## 它解决什么问题

工作经常被拆到不同的对话里：A 框做调研，B 框动手实现，而两边互相看不见。
你问一句"我们在那个框里定了啥来着？"，诚实的回答只有两种：*"我不知道"*，或者
*"你贴过来"*——后者要把整份对话塞进上下文。

这个东西给出第三个答案：**按需去读，只把有用的那几行带回来。**

```
$ sess.js timeline "发布清单"
=== 发布清单   263 条消息, 09-25 11:25 -> 09-25 13:04
  09-25 11:25 [2]  把新的构建路径端到端验一遍
  09-25 11:32 [26] 特效应该在任务结束后自己淡出，而不是还问我
  09-25 11:41 [56] 先打开加速器，然后找到编辑器
  ...
```

磁盘上三个对话加起来 6 MB、655 条消息，一次检索只读进几段片段，其余一条都不加载。

## 默认作用域 = 当前对话

跨对话检索是**刻意做成需要显式开启**的：

| 不用问就能做 | 必须你明确要求 |
|---|---|
| `whoami`、`list`、`turns`、`grep <词>` | `grep <词> --all`、`list --all` |
| 读**当前**对话 | 读**其它**对话（须指名） |

单独跑 `list` 时，**连其它对话的标题都不会显示**——它只告诉你"磁盘上还有 N 个"，就停下。
"为了获取上下文"去翻别人的其它聊天，正是这个工具被设计成**不会变成**的样子，
所以给 agent 看的 `SKILL.md` 里，第一节就写死了这条规则。

## 命令

| 命令 | 作用 |
|---|---|
| `whoami` | 当前是哪个对话（id、标题、文件、最后更新） |
| `list [--all]` | 对话索引：id、消息数、最后更新、标题 |
| `turns [N]` | 当前对话最近 N 条 |
| `grep <词> [N] [--all]` | 检索，命中的每条给一段前后文；`--all` 才跨对话 |
| `read <目标> [N]` | 读某个对话的消息 |
| `tools <目标> [N]` | 它实际调用了哪些工具 —— 真正动了什么 |
| `timeline <目标>` | 一行一条人的指令：这个对话的脉络 |
| `msg <目标> <n>` | 读第 n 条的完整原文（编号用 `timeline` 打印的） |

加 `--raw` 会把宿主自己注入的消息（运行时上下文、技能目录、后台任务通知）也带上。
默认过滤掉，因为在长会话里它们比真实发言还多，会让时间线根本没法看。

## 环境要求

**Node 22+。** 就这一条。没有包、不用编译、不用安装。

## 最有意思的部分：对话文件到底是什么格式

如果你想自己读这些文件，这段能帮你省下一个下午。

```
~/.dsh/sessions/<工作区>/<对话-id>/session.v4.jsonl.zstd   转录正文
~/.dsh/storages/workspace.json                             对话索引
~/.dsh/storages/session_projcache/sessions/<对话-id>.json   标题、token 统计
```

**那个 `.zstd` 不是一条压缩流。** 它是追加写入的日志，大约 **1500 个彼此独立的 zstd 帧**，
每 flush 一次一帧。所以 `zstdDecompressSync()` 和流式 `createZstdDecompress()` **都只吃第一帧、
吐出 252 字节**——看起来就像"这个对话是空的"，然后你就会去一个完全错误的方向找 bug。

真正的读法是扫帧魔数 `28 B5 2F FD`，按边界逐帧解压再拼接。
帧体理论上可能凑巧包含这几个字节，所以解不出来的帧要向后合并直到能解开。
会话正在进行时，末尾出现半个帧是正常的，跳过即可。
实测一个真实的 2 MB 会话：**1552 帧、0 失败、解出 7 MB JSONL、2416 条记录。**

Node 22+ 的 `zlib` 自带 zstd，所以这东西才能做到零依赖。

记录是 JSONL。值得知道的三种：

| 记录 | 文本在哪 |
|---|---|
| `user/message` | `data.content[]` 里 `type === "text"` 的项；`data.source.kind` 说明这条到底是人说的（`user`）、权限变更（`user-approval`），还是宿主注入的样板（`runtime-context`、`skill-catalog`、`tool-jobs`） |
| `assistant/message` | `data.message.content[]` 里 `type === "text"` 的项 —— **思考块和它在同一个数组里**，所以必须按 `type` 过滤 |
| `tool/call` | `data.name` + `data.arguments` |

## 作为 agent skill 使用

`SKILL.md` 带 front-matter、带作用域规则，就是为直接塞进 agent 上下文而写的。
把它和 `scripts/` 一起放进你的技能目录即可。

### 关于可移植性

front-matter 用的是开放的 **Agent Skills** 格式 —— `name` 加 `description` ——
Claude Code、Codex、DSH 三家都读这个。**`description` 是"路由契约"**：
agent 先看到它，才决定要不要加载这个技能。所以它必须同时说清楚"什么时候该用"和
"什么时候不该用"。**把 front-matter 删掉不会让技能"更简单"，只会让它彻底不可见。**

在宿主之间能搬走的是**格式和指令**，搬不走的往往是技能**调用的外部东西**。
这份是纯 Node、零依赖，所以只要 Node 22+ 在哪都能跑；
而一个假设了 `bash`、macOS 路径、或某个宿主专有工具的技能，就搬不过去。

## 限制

- 只对磁盘上还存在的对话有效。
- **正在进行的**对话，最后几个帧可能还没 flush，所以可能差一两条消息。
- 它按实测的转录格式来读。如果宿主改了格式，`readRecords()` 是唯一需要修的函数。
